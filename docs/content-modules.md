# Content Modules

MaaGE supplies mechanisms; statically linked modules register content and policy. `MaaGE::Base` is an ordinary `maage_content_module` selected by `src/application/content_modules.c` for Client and Server. The authoritative signatures and lifetime comments are in `include/maage/content.h`.

## Composition and Lifetime

`maage_content_config.modules` submits root modules (`minecraft`, `ie2`) or submodules (`ie2:expanded`). Identities use lowercase letters, digits, `_`, `-` and `.` in each nonempty segment, with zero or one colon. A submodule's root must exist and appear explicitly in its dependency array. No dependency is inserted automatically. The existing stable topological sorter rejects duplicate modules/dependencies, missing dependencies and cycles, choosing the earliest submitted ready module for deterministic numeric assignment.

Every applicable module completes the current stage before the next begins: **DEFINE → BIND, INTERNAL → BIND, EXTERNAL → BIND, COMPATIBILITY → FINALIZE → LOAD → INITIALIZE**. The full public phase constants and callbacks use `INTERNAL`, `EXTERNAL` and `COMPATIBILITY` without compatibility aliases. INTERNAL resolves a module's own relationships; EXTERNAL resolves declared dependencies and requires at least one; a non-NULL COMPATIBILITY callback declares explicit integration work. Missing callbacks do nothing and produce no skip logs. Finalization validates references and freezes logical definitions; Server omits LOAD and initializes after peer validation. Client initialization waits for required physical resources.

`minecraft` is the ordinary built-in root module. It registers `minecraft:*`, binds internal references in INTERNAL, and declares no EXTERNAL, COMPATIBILITY or initializer. Recipes, smelting, fluids, containers, sounds, Creative and generation retain public registrations.

A root owns its namespace; submodules share that namespace without owning existing parent/sibling definitions. Composition-local registry scopes enforce ownership across named blocks, items, biomes, fluids, geometry, containers, Creative tabs, sounds, entity types, models, block-entity codecs and generation registrations. Duplicate identities, foreign updates and conflicting singleton bindings fail. Unregistration and intentional replacement remain unsupported. Failed registration must abort its callback; ignored ownership violations still fail composition.

Name resolution and `maage_content_module_data` require an explicit direct dependency for another module's content/state; INTERNAL permits only the current module. Numeric getters remain direct O(1) services for trusted native code. No name resolution is added to gameplay loops.

`module_data` survives a module's phases. `maage_content_own` transfers data on success and destroys it after the registries. Config borrows through creation; `context.trace` borrows only through its current lifecycle call; descriptor arrays, names and callbacks outlive the content and any independently composed Server using them. Callback code and registered state outlive Worlds, jobs and audio/visual readers. Stop all consumers before destroying content. Independent compositions must use per-context owned state rather than mutate static module data.

## Tags, Properties and Behaviors

`maage_content_context.traits` owns the shared logical composition registry. Register properties with `maage_property_register`: booleans, bounded unsigned integers, or extensible identity values registered with `maage_property_value_register`. Identity values carry their own namespaced identities and may be added by dependent modules. Zero is a valid property/tag/provider/value ID; `MAAGE_CONTENT_ID_INVALID` is the invalid sentinel. Property configuration zero is the empty configuration.

`maage_property_set_register` copies, validates, sorts and interns unique assignments during composition. Blocks store a configuration ID in each explicitly registered state. `maage_block_state_value` inspects state or type constants; `maage_block_state_change` resolves an already registered configuration and the encountered block's numeric state without allocation. Sparse registration keeps invalid combinations absent and avoids automatic Cartesian products. Presentation caches contain resolved geometry, light and textures; render loops do not interpret semantic properties.

`maage_tag_register` accepts domain masks, required property IDs, included tags and behavior IDs. Includes flatten into one effective contract. `maage_traits_assign` assigns owned block/item definitions their tags and type constants. Every block requires at least one tag; zero-property classification tags are valid. A contract's required property is satisfied by either a type constant or a state/variant assignment. Constants cannot be overridden by state assignments. Duplicate assignments, incompatible domains, missing required properties and invalid typed values fail composition. Tags carry no engine-defined meanings. The `minecraft` module registers its own wood/log/planks/leaves/soil classifications and semantic schemas through these APIs.

Behavior providers have an event, borrowed immutable provider context, callback, explicit numeric order and optional earlier-provider dependencies. Tag composition deduplicates the same provider, orders composed handlers deterministically and rejects exclusive conflicts or equal-order handlers without a dependency relationship. A failed handler stops dispatch with its originating Status; warnings remain visible. Support adapters combine predicates with AND. Provider context belongs to the provider independently of the block adopting the tag. Block lifecycle callback fields are finalized dispatch surfaces: register providers on tags, then let finalization install the typed adapters. Uncomposed registration callbacks fail explicitly rather than being silently replaced. Providers use the same owner lifecycle as ordinary content.

Tool eligibility, mining speed and conditional wear match registered item-domain capability tags; the Base module owns pickaxe/shovel/axe/shears/hoe classification. Generic engine code contains no fixed tool-category enumeration.

Items own contiguous local variant IDs, each with a validated property configuration and copied appearance/placement row. Variant zero is the ordinary default; count and damage remain separate mutable stack fields. There is one variant representation, shared by inventory, Creative, recipes, smelting, entities and persistence. Recipe choices can match item identities or item-domain tags, optionally constrained by typed properties. Output projections relate source-ingredient properties to output-tag candidates; finalization rejects absent or ambiguous outputs and compiles numeric result maps. This allows a dependent module's log and plank variants to participate without editing the original recipe.

Traits finalize after all binding phases and before block/item registries. Finalized membership uses numeric bitsets; event chains and property configurations are immutable and allocate nothing during runtime queries. Client presentation views borrow the logical registry. Peer validation compares schemas, names, values, configurations, contracts and dispatch identity while allowing independent callback addresses and provider contexts.

## Execution Context and Bootstrap

`execution.h` supplies a copyable side/capability value: Client, integrated Server or dedicated Server. Client has presentation configuration; both Server sides have authority and are headless. Presentation capability does not promise a live rendering/audio device. There is no mutable global side. Lifecycle callbacks receive `context.execution`; runtime code can retain a copy, query `maage_content_execution`, or query `maage_world_execution` when World is available. Capabilities describe facilities rather than executable names or operating systems.

Shared DEFINE/bind callbacks are pure composition work. Optional `side_bind_internal`, `side_bind_external` and `side_bind_compatibility` execute at their corresponding stage only for the descriptor's `sides` mask. `initialize` uses the same mask. Zero selects no side hooks/initializer. A selected callback fails if `required_capabilities` are unavailable. EXTERNAL still requires dependencies; a declared COMPATIBILITY callback is the explicit compatibility condition. No optional-dependency discovery or undeclared compatibility targets are implemented.

Client creates one finalized logical composition. `maage_client_resources_load` consumes its numeric presentation sources directly; there is no preliminary composition. LOAD decodes sources, constructs the atlas and samples colormaps. `maage_content_view_create` copies resolved state/geometry appearances and biome colors while borrowing immutable logical names, types, items and behavior. It performs no registration or finalization. These immutable presentation snapshots are independently destroyable and can be created repeatedly. `maage_content_load_complete` publishes Client readiness; `maage_content_initialize` rejects repeated or premature initialization. Resource refreshes never call initialization.

Integrated Server obtains the same submitted descriptors through the finalized Client identity peer, independently composes headless content on its owner thread, validates numeric identities, then initializes before opening World/storage or publishing packets. Dedicated Server does the same with its dedicated context and application composition. Neither requires Client resources or devices. Entity and model definitions compose on both sides; only Client LOAD creates texture sheets and GPU geometry.

Peer validation compares named domain/owner/ID maps, typed property schemas/identity values, flattened tag contracts/membership, behavior ordering, state `(block, properties)` maps and item variant configurations, logical texture descriptors and Creative entry identities. Behavior callbacks and runtime-owned state may differ with coherent IDs. Side-only registrations remain supported for independent compositions; mismatching session peers are rejected. Remote negotiation, hidden Server-only IDs crossing a session and optional-dependency discovery remain unimplemented.

## Diagnostics

Central Log category `maage.content` retains shared lifecycle summaries with explicit sides. DEBUG produces at most one completion per module per phase that executed callbacks, including both shared and side work. Dependency validation/order remain available at DEBUG. Empty callbacks/phases produce no ordinary lines. Failures retain original Status/trace, exact module/phase, dependency/registry, offending identity where known and reason. INFO summarizes composition, finalization, LOAD and initialization. See the Client presentation document for reload publication and the logging policy.

## Extension Interfaces

| Interface | Contract |
| --- | --- |
| `traits.h` | Composition-owned typed schemas, extensible identity values, interned property configurations, domain-aware tags and deterministic provider dispatch. |
| `blocks.h`, `items.h`, `biome.h`, `presentation.h` | Immutable finalized numeric definitions and behavior/presentation metadata. |
| `creative.h` | Explicit Creative tab identities, titles, icons/backgrounds, order and obtainable variant entries. Finalized tab/search views borrow numeric entry IDs; item validity never implies visibility. |
| `containers.h` | Copied layouts, slot/progress descriptors and Server-owner open/access/policy/action/sample/retryable-close callbacks. Independently paged transport windows do not cap registrations. Transaction failure retains item ownership; custom backing stores stay module-owned. |
| `fluids.h` | Fluid identities and copied state maps for schedules, propagation, contact, physics, material and immersion; finalized dispatch is numeric. |
| `block_geometry.h` | Optimized primitives or immutable worker-safe quad providers. Allocation-free count/write passes agree; collision/selection bounds are separate from visual geometry. |
| `entity_types.h`, `entities.h` | Registered living/projectile definitions, copied loot and biome spawn rules, owner behavior/interaction callbacks, independent flat instance state and explicit versioned codecs; World retains item/falling/living/projectile instances. |
| `models.h` | Copied transformable parts/cuboids, numeric texture/material references, named channels resolved at boundaries, geometry providers and hierarchy/animation callbacks. Client caches emitted geometry per immutable resource generation. |
| `sounds.h` | Registered resources/events/music/ambience independent of playback; Client owns decode, voice and device capacity. |
| `crafting.h`, `smelting.h` | Numeric recipes, smelting and fuel policy used by the authoritative owner. |

No API registry has an artificial limit derived from transport page size, GPU working set or simultaneous sound voices. Saved block/state/item/item-variant/biome/entity-type IDs use the World dictionary; other runtime IDs follow the deterministic current composition.

Entity types, live instances, block entities and presentation models remain distinct facilities. `maage_entity_type_register` assigns a type ID; `maage_entities_spawn_type` assigns an instance ID. `maage_entity_type_update` binds copied references before finalization. Runtime definitions and callbacks borrow module context; each instance and checkpoint owns its flat custom state. `maage_item_registry_bind_model` changes only item presentation; item placement and inventory ownership stay in their existing paths. Dynamic module loading/discovery, scripting and remote content negotiation are not implemented.

## Creative Catalogs

`maage_content_context.creative` owns the presentation catalog alongside the existing item and container registries; it owns no inventory. Register tabs with `maage_creative_tab_register` in DEFINE, retain returned IDs (or resolve names at module boundaries), and add individual variants with `maage_creative_entry_register` in DEFINE or the appropriate binding stage. `maage_content_creative` exposes the finalized catalog to frontends and the Server. `src/base/creative.c` registers the twelve built-in tabs and their explicit assignments using these same APIs.

Tab `order` sorts independently of numeric registration identity. Category entries have separate `order` and `search_order`, an explicit count-one/pristine stack, optional copied tooltip lines and a `searchable` flag. Item definitions may also supply immutable variant-specific tooltip lines through their `tooltip` callback; search and ordinary item hover share them. Search and inventory are optional singleton presentation roles. Finalization validates referenced items, variants and registered textures, creates ordered per-tab views, and deduplicates searchable item/variant pairs. There is no implicit enumeration through a numeric variant range. Registration may move definition arrays; retain numeric IDs until finalization.

Tabs can use an existing item stack as their icon or copied textured quads in a 16x16 cell. Presentation-only icons do not register obtainable items. GUI backgrounds and tab sprites use the ordinary presentation atlas, including its resource failure handling. A personal container with `creative_catalog` uses the shared 195x136 layout, 256-pixel tab sprite sheet and real player inventory. Category pages show ten tabs while Search and Survival Inventory stay available. Neither catalog entries nor presentation tab IDs are persisted as gameplay stacks.
